# راهنمای جامع سرور، دستگاه، WordPress، UI، MQTT و OTA

> **نسخه:** 1.0  
> **مخاطب:** توسعه‌دهنده Backend، توسعه‌دهنده WordPress، برنامه‌نویس ESP32، اپراتور سیستم  
> **هدف:** این سند مرجع اجرایی و قرارداد تبادل دادهٔ پلتفرم Gadget است. برای شروع، تغییر، تست و بهره‌برداری روزانه به همین سند رجوع کنید.

---

## 1. تصویر کلی سیستم

مسیر اصلی داده به این شکل است:

```text
WordPress ──Webhook / Pull Sync──> Django API + PostgreSQL
                                        │
                           Redis + Celery Worker / Beat
                                        │
                              MQTT (Mosquitto)
                                        │
                                  ESP32 Device
                                        │
                     REST: Config / Heartbeat / OTA Report
```

### نقش اجزا

| جزء | مسئولیت |
|---|---|
| **Django API** | API دستگاه، webhook WordPress، ساخت config، پنل Admin، OTA و metrics |
| **PostgreSQL** | دادهٔ دائمی دستگاه، template، eventهای sync، firmware و وضعیت‌ها |
| **Redis** | broker مربوط به Celery و cache/queue آینده |
| **Celery Worker** | اجرای jobهای غیرهمزمان: MQTT، sync و monitor |
| **Celery Beat** | اجرای زمان‌بندی‌شدهٔ health check، stale device و pull sync |
| **Mosquitto** | اطلاع‌رسانی بلادرنگ به دستگاه‌ها؛ config change و فرمان‌های آینده |
| **WordPress** | منبع اصلی اطلاعات مشتری، plan، دستگاه و datasource |
| **Django Admin** | پنل عملیاتی برای مدیریت داده‌های پویا، firmware و مشاهدهٔ وضعیت |

### قانون مالکیت داده

- WordPress مالک رکوردهای مشتری، plan و اطلاعات تجاری است.
- Django یک **local mirror** برای اجرای سریع و مستقل دستگاه‌ها نگه می‌دارد.
- Firmware، وضعیت heartbeat، deployment OTA و health سرویس‌ها در Django مدیریت می‌شوند.
- ESP32 هرگز نباید مستقیماً به WordPress وابسته باشد.

## 2. استقرار روی سرور Linux

### پیش‌نیازها

- سرور Ubuntu 22.04/24.04 LTS یا Debian جدید با حداقل 2 vCPU، 4GB RAM و 40GB دیسک.
- یک domain مانند `api.example.com` با DNS A record به IP سرور.
- Docker Engine، Docker Compose plugin، Git، Nginx و Certbot.
- دسترسی SSH با کلید؛ ورود مستقیم root و password login غیرفعال باشد.

### 2.1 آماده‌سازی Ubuntu

روی سرور با کاربر دارای sudo اجرا کنید:

```bash
sudo apt update && sudo apt -y upgrade
sudo apt install -y ca-certificates curl git make nginx certbot python3-certbot-nginx ufw

# نصب Docker Engine طبق راهنمای رسمی Docker
curl -fsSL https://get.docker.com | sudo sh
sudo usermod -aG docker "$USER"
newgrp docker

# firewall: فقط SSH، HTTPS، HTTP و MQTT امن
sudo ufw allow OpenSSH
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp
sudo ufw allow 8883/tcp
sudo ufw enable
```

پورت‌های PostgreSQL، Redis و API نباید از اینترنت قابل دسترسی باشند. فایل production این پروژه فقط API را روی `127.0.0.1:8000` expose می‌کند؛ Nginx تنها ورودی HTTP/HTTPS است.

### 2.2 دریافت پروژه و ساخت secretها

```bash
sudo mkdir -p /opt/gadget
sudo chown "$USER":"$USER" /opt/gadget
git clone https://github.com/VahidMB/New-Gadget-Project.git /opt/gadget/app
cd /opt/gadget/app
cp .env.example .env.production
chmod 600 .env.production
```

### ایجاد تنظیمات محیط

فایل `.env.production` حاوی secretها است و نباید commit یا در log چاپ شود. مقادیر production نمونه:

```dotenv
DJANGO_SECRET_KEY=<random-long-secret>
DJANGO_DEBUG=0
DJANGO_SECURE_SSL_REDIRECT=1
DJANGO_ALLOWED_HOSTS=api.example.com

POSTGRES_DB=gadget
POSTGRES_USER=gadget
POSTGRES_PASSWORD=<strong-password>
POSTGRES_HOST=db
POSTGRES_PORT=5432

REDIS_URL=redis://redis:6379/0
CELERY_BROKER_URL=redis://redis:6379/0

MQTT_HOST=mqtt
MQTT_PORT=8883
MQTT_TOPIC_ROOT=gadget/v1
MQTT_USERNAME=<broker-user>
MQTT_PASSWORD=<broker-password>
MQTT_USE_TLS=1
MQTT_CERTS_DIR=/etc/letsencrypt/live/mqtt.example.com
MQTT_PASSWORD_FILE=/opt/gadget/mosquitto/passwordfile

WORDPRESS_WEBHOOK_SECRET=<long-random-secret>
WORDPRESS_SYNC_TRIGGER_TOKEN=<long-random-secret>
WORDPRESS_WEBHOOK_MAX_AGE_SECONDS=300

METRICS_TOKEN=<long-random-secret>
DEVICE_HEARTBEAT_STALE_AFTER_SECONDS=300
```

مقدارهای secret را با ابزار امن تولید کنید:

```bash
openssl rand -base64 48
```

### 2.3 TLS برای API

ابتدا در فایل [deploy/linux/gadget-api.nginx.conf](../../deploy/linux/gadget-api.nginx.conf) مقدار `YOUR_DOMAIN` را با domain واقعی جایگزین کنید. سپس:

```bash
sudo cp deploy/linux/gadget-api.nginx.conf /etc/nginx/sites-available/gadget-api
sudo ln -s /etc/nginx/sites-available/gadget-api /etc/nginx/sites-enabled/gadget-api
sudo rm -f /etc/nginx/sites-enabled/default
sudo nginx -t && sudo systemctl reload nginx
sudo certbot --nginx -d api.example.com
```

### 2.4 TLS و user برای MQTT

برای MQTT یک domain جدا مثل `mqtt.example.com` تنظیم کنید و certificate آن را با Certbot بگیرید. سپس password file بسازید:

```bash
sudo mkdir -p /opt/gadget/mosquitto
docker run --rm -it -v /opt/gadget/mosquitto:/work eclipse-mosquitto:2 \
  mosquitto_passwd -c /work/passwordfile DEVICE_OR_SERVICE_USER
chmod 600 /opt/gadget/mosquitto/passwordfile
```

فایل [deploy/linux/mosquitto.production.conf](../../deploy/linux/mosquitto.production.conf) برای TLS و عدم اجازهٔ anonymous آماده است. قبل از عمومی کردن MQTT، ACL per-device نیز اضافه کنید.

### 2.5 اجرای production

```bash
cd /opt/gadget/app
docker compose --env-file .env.production -f deploy/linux/docker-compose.production.yml up -d --build
docker compose --env-file .env.production -f deploy/linux/docker-compose.production.yml ps
docker compose --env-file .env.production -f deploy/linux/docker-compose.production.yml logs -f
```

Compose production این سرویس‌ها را اجرا می‌کند:

| سرویس | آدرس داخل Docker | پورت میزبان | توضیح |
|---|---|---:|---|
| `api` | `api:8000` | `127.0.0.1:8000` | Django + Gunicorn؛ فقط Nginx به آن دسترسی دارد |
| `worker` | - | - | Celery worker |
| `beat` | - | - | زمان‌بند Celery |
| `db` | `db:5432` | ندارد | PostgreSQL داخلی |
| `redis` | `redis:6379` | ندارد | Redis داخلی |
| `mqtt` | `mqtt:8883` | `8883` | Mosquitto TLS برای ESP32 |

### Migration و Admin

در اولین اجرا API migration را اجرا می‌کند؛ برای اعمال دستی و ساخت مدیر:

```bash
docker compose --env-file .env.production -f deploy/linux/docker-compose.production.yml exec api python manage.py migrate
docker compose --env-file .env.production -f deploy/linux/docker-compose.production.yml exec api python manage.py createsuperuser
```

سپس پنل را باز کنید:

```text
https://api.example.com/admin/
```

### بررسی سریع

```bash
curl https://api.example.com/api/v1/health/
docker compose --env-file .env.production -f deploy/linux/docker-compose.production.yml exec api python manage.py check_services
```

## 4. مدل داده و رابطه‌ها

### دستگاه

`WordPressDevice` نسخهٔ local دستگاه WordPress است.

| فیلد | مفهوم |
|---|---|
| `external_id` | شناسهٔ پایدار دستگاه؛ در URL و Topic استفاده می‌شود |
| `serial_number` | سریال سخت‌افزار |
| `hardware_model` | مدل دقیق سخت‌افزار؛ برای انتخاب firmware ضروری است |
| `plan` | `simple` یا `pro`؛ ورودی‌هایی مثل `vip` و `premium` به `pro` نرمال می‌شوند |
| `is_active` | اجازهٔ سرویس‌دهی به دستگاه |
| `provisioning_state` | `unprovisioned`، `provisioned` یا `suspended` |
| `device_token_hash` | فقط hash توکن؛ plaintext ذخیره نمی‌شود |
| `custom_config` | تنظیمات اختصاصی دریافت‌شده از WordPress |
| `effective_config` | config نهایی قابل ارسال به دستگاه |
| `ui_version` | نسخهٔ monotonic تنظیمات UI |

### وضعیت دستگاه

هر دستگاه حداکثر یک `DeviceStatus` دارد:

| فیلد | مفهوم |
|---|---|
| `status` | `online`، `offline`، `updating` یا `error` |
| `last_heartbeat_at` | آخرین پیام معتبر دستگاه |
| `last_config_version` | آخرین `ui_version` اعمال‌شده روی دستگاه |
| `firmware_version` | نسخهٔ firmware گزارش‌شده |
| `battery_level` | عدد صحیح 0 تا 100 |
| `signal_strength` | RSSI، معمولاً عدد منفی dBm |
| `error_message` | پیام خطای آخر دستگاه |

### UI

```text
UITemplate
  └── UIPage (چند صفحه)
        └── UIElement (چند عنصر)
```

- Template بر اساس `plan_type` و `is_active` انتخاب می‌شود.
- هر صفحه `page_key`، نوع، ترتیب (`priority`) و refresh interval دارد.
- هر عنصر نوع، label، source key، جایگاه، style و config دارد.
- اگر template فعال وجود نداشته باشد، سرور از config پیش‌فرض `simple` یا `pro` استفاده می‌کند.

### OTA

```text
FirmwareRelease
  └── FirmwareDeployment (برای هر device + release)
```

- هر release برای یک `hardware_model` و version یکتا است.
- هر deployment نتیجهٔ دانلود/نصب یک release روی یک دستگاه را نگه می‌دارد.

## 5. چرخهٔ عمر دستگاه و امنیت

### 5.1 ساخت دستگاه

دستگاه معمولاً از یکی از این راه‌ها ایجاد می‌شود:

1. Webhook WordPress با event دستگاه.
2. Pull Sync از endpointهای WordPress.
3. ساخت دستی در Django Admin برای آزمایش.

رکورد تازه در حالت `unprovisioned` است و به API دستگاه دسترسی ندارد.

### 5.2 Provision کردن

پس از ساخت device، توکن اختصاصی تولید کنید:

```bash
docker compose exec api python manage.py provision_device ESP32-ABC123
```

خروجی نمونه:

```text
QfBqH9u3...token...
```

**قواعد امنیتی:**

- این token را در secure storage دستگاه یا فرایند manufacturing ذخیره کنید.
- توکن در دیتابیس به‌صورت hash ذخیره می‌شود؛ بعداً قابل مشاهده نیست.
- اگر token لو رفت، آن را rotate کنید.
- `suspended` یا `is_active=false` دسترسی API دستگاه را قطع می‌کند.

### 5.3 هدر اجباری دستگاه

همهٔ درخواست‌های device API این هدر را دارند:

```http
X-Device-Token: <device-token>
```

در نبود یا اشتباه‌بودن توکن، پاسخ `401` است. دستگاه unprovisioned/suspended/inactive پاسخ `403` می‌گیرد.

## 6. قرارداد API

تمام APIها زیر prefix زیر هستند:

```text
/api/v1/
```

### 6.1 Health API

```http
GET /api/v1/health/
```

نمونه پاسخ:

```json
{
  "status": "ok",
  "service": "gadget-api",
  "services": {
    "api": {
      "label": "API",
      "status": "up",
      "response_time_ms": 2,
      "last_check_at": "2026-09-22T10:00:00+00:00",
      "stale": false
    },
    "db": {
      "label": "Database",
      "status": "up",
      "response_time_ms": 8,
      "last_check_at": "2026-09-22T10:00:00+00:00",
      "stale": false
    }
  }
}
```

حالت‌های وضعیت کل: `ok`، `degraded`، `down` و `unknown`. اگر سرویس down باشد HTTP status برابر `503` می‌شود.

### 6.2 دریافت config نمایشگر

```http
GET /api/v1/devices/{external_id}/display-config/
X-Device-Token: <token>
```

```bash

{

    "ui_version": 1,

    "template": {"name": "Pro Dashboard", "version": "2.0"},
    "theme": {"name": "dark", "primary_color": "#00B7FF"},
    "screen": {"orientation": "portrait", "width": 320, "height": 480},
    "pages": [
      {
        "key": "home",
        "type": "dashboard",
        "priority": 0,
        "refresh_interval_ms": 60000,
        "visible_when": {},
        "elements": [
          {
            "type": "text",
            "label": "Temperature",
            "source_key": "weather.temperature",
            "position": {"x": 10, "y": 20, "width": 200, "height": 40},
            "font_size": "24",
            "color": "#FFFFFF",
            "style": {},
            "z_index": 1,

    ]

```

**نکتهٔ مهم:** `ui_version` بیرونی نسخهٔ sync دستگاه است؛ `effective_config.ui_version` نسخهٔ قرارداد render است. Firmware باید وقتی `ui_version` سرور از `last_config_version` محلی بزرگ‌تر است config را دریافت و اعمال کند.

### 6.3 Heartbeat

```http
POST /api/v1/devices/{external_id}/heartbeat/
Content-Type: application/json
X-Device-Token: <token>
```

Payload:

```json
{
  "status": "online",
  "firmware_version": "1.3.0",
  "battery_level": 84,
  "signal_strength": -57,
  "config_version": 7,
  "error_message": ""
}
```

قواعد validation:

- `status`: یکی از `online`، `offline`، `updating`، `error`.
- `battery_level`: عدد صحیح بین 0 و 100.
- `signal_strength` و `config_version`: عدد صحیح.
- همهٔ فیلدها به جز `status` اختیاری‌اند؛ مقدار پیش‌فرض status برابر `online` است.

پاسخ:

```json
{
  "acknowledged": true,
  "device_id": "ESP32-ABC123",
  "status": "online",
  "last_heartbeat_at": "2026-09-22T10:00:00+00:00"
}
```

پیشنهاد ارسال:

| وضعیت | فاصلهٔ پیشنهادی |
|---|---:|
| online عادی | هر 60 تا 120 ثانیه |
| idle کم‌مصرف | حداکثر هر 5 دقیقه |
| updating | هر 10 تا 30 ثانیه |
| error | هر 30 تا 60 ثانیه |

Celery هر دقیقه statusهای `online` و `updating` را بررسی می‌کند. اگر فاصله از `DEVICE_HEARTBEAT_STALE_AFTER_SECONDS` بیشتر باشد، وضعیت `offline` می‌شود.

### 6.4 OTA: بررسی update

```http
GET /api/v1/devices/{external_id}/firmware/update-check/?firmware_version=1.3.0
X-Device-Token: <token>
```

پاسخ بدون update:

```json
{
  "update_available": false,
  "firmware_version": "1.3.0"
}
```

پاسخ با update:

```json
{
  "update_available": true,
  "deployment_id": 42,
  "version": "1.4.0",
  "download_url": "https://firmware.example.com/esp32-s3-1.4.0.bin",
  "checksum_sha256": "64-character-lowercase-sha256",
  "mandatory": false,
  "release_notes": "Bug fixes and improved Wi-Fi recovery"
}
```

Firmware باید:

1. URL را فقط از HTTPS دانلود کند.
2. SHA-256 فایل دریافت‌شده را محاسبه کند.
3. با `checksum_sha256` مقایسه کند.
4. فقط در صورت برابر بودن نصب کند.
5. قبل و بعد از نصب، Heartbeat با `updating`/`online` ارسال کند.
6. نتیجه را report کند.

### 6.5 OTA: گزارش نتیجه

```http
POST /api/v1/devices/{external_id}/firmware/update-report/
Content-Type: application/json
X-Device-Token: <token>
```

نصب موفق:

```json
{
  "release_version": "1.4.0",
  "status": "installed",
  "firmware_version": "1.4.0",
  "error_message": ""
}
```

خطا:

```json
{
  "release_version": "1.4.0",
  "status": "failed",
  "firmware_version": "1.3.0",
  "error_message": "SHA-256 mismatch"
}
```

وضعیت‌های مجاز: `pending`، `downloading`، `installed`، `failed`، `skipped`.

### 6.6 Prometheus metrics

```http
GET /api/v1/metrics/
Authorization: Bearer <METRICS_TOKEN>
```

اگر `METRICS_TOKEN` خالی باشد، endpoint در محیط local بدون token کار می‌کند. در production حتماً token تنظیم و endpoint در شبکهٔ monitoring محدود شود.

Metrics فعلی شامل شمار device بر اساس status و up/down بودن آخرین health سرویس است.

## 7. WordPress Integration

### 7.1 Webhook

```http
POST /api/v1/integrations/wordpress/webhook/
Content-Type: application/json
X-WP-Timestamp: <unix-seconds>
X-WP-Signature: <HMAC-SHA256>
```

امضا با این داده ساخته می‌شود:

```text
{timestamp}.{raw-request-body}
```

و secret برابر `WORDPRESS_WEBHOOK_SECRET` است. سرور موارد زیر را بررسی می‌کند:

1. وجود timestamp و signature.
2. معتبر بودن HMAC-SHA256.
3. نبودن timestamp در آینده.
4. کمتر بودن سن پیام از `WORDPRESS_WEBHOOK_MAX_AGE_SECONDS`.

نمونه payload دستگاه:

```json
{
  "event": "device.updated",
  "entity_type": "device",
  "entity": {
    "external_id": "ESP32-ABC123",
    "customer_external_id": "customer-91",
    "serial_number": "SN-001",
    "hardware_model": "esp32-s3-display-v1",
    "name": "Lobby Display",
    "plan": "pro",
    "is_active": true,
    "updated_at": "2026-09-22T10:00:00Z",
    "custom_config": {
      "theme": {"primary_color": "#FF9900"},
      "screens": [{"type": "weather", "enabled": true}]
    },
    "metadata": {
      "location": "Tehran Office"
    }
  }
}
```

نمونه datasource:

```json
{
  "event": "data_source.updated",
  "entity_type": "data_source",
  "entity": {
    "external_id": "weather-tehran",
    "key": "weather.tehran",
    "label": "Tehran Weather",
    "enabled": true,
    "config": {
      "provider": "openweathermap",
      "refresh_seconds": 900,
      "units": "metric"
    }
  }
}
```

مقادیر `entity_type` معتبر: `device` و `data_source`.

### 7.2 Pull Sync

```http
POST /api/v1/integrations/wordpress/sync/
X-Sync-Token: <WORDPRESS_SYNC_TRIGGER_TOKEN>
```

سرور دو endpoint WordPress را می‌خواند:

```dotenv
WORDPRESS_DEVICES_ENDPOINT=/wp-json/gadget/v1/devices
WORDPRESS_DATA_SOURCES_ENDPOINT=/wp-json/gadget/v1/data-sources
```

هر endpoint می‌تواند array مستقیم یا object با کلید `items` برگرداند:

```json
{"items": [{"external_id": "ESP32-ABC123"}]}
```

Celery Beat pull sync را هر 15 دقیقه اجرا می‌کند. Webhook برای تغییر فوری است و Pull Sync نقش recovery دارد.

### 7.3 تغییرات در schema WordPress

برای افزودن فیلد:

1. فیلد را ابتدا در قرارداد WordPress ثبت کنید.
2. نمونه webhook و pull-sync را به‌روزرسانی کنید.
3. اگر فیلد باید دائمی باشد، آن را به مدل Django و migration اضافه کنید.
4. `_upsert_device` یا `_upsert_data_source` در [backend/core/services.py](../backend/core/services.py) را تغییر دهید.
5. test برای payload جدید بنویسید.
6. firmware را تنها بعد از سازگارشدن backend و قرارداد update کنید.

فیلدهای ناشناخته را می‌توان موقتاً در `metadata`/`config` نگه داشت؛ برای query، filter یا رفتار رسمی باید ستون مدل تعریف شود.

## 8. UI، Template و منابع داده

### 8.1 Simple و Pro

| قابلیت | Simple | Pro |
|---|---|---|
| config ثابت پایه | بله | خیر |
| custom UI | خیر | بله |
| theme سفارشی | خیر | بله |
| page و element سفارشی | محدود به template پایه | بله، براساس PlanRule |

- در simple، custom config WordPress نباید قرارداد ثابت محصول را بشکند.
- در pro، custom config با template پایه merge می‌شود.

### 8.2 ساخت Template در Django Admin

1. وارد `/admin/` شوید.
2. در **UI Templates** یک template بسازید.
3. `plan_type` را `simple` یا `pro` انتخاب کنید.
4. `is_active` را فعال کنید.
5. در inline **UI Pages** صفحه اضافه کنید.
6. داخل هر page، **UI Elements** اضافه کنید.

برای هر `UIElement`:

| فیلد | نمونه | استفاده در Firmware |
|---|---|---|
| `element_type` | `text`, `image`, `chart` | نوع widget renderer |
| `label` | `Temperature` | متن ثابت |
| `source_key` | `weather.temperature` | کلید دادهٔ پویا |
| `x`, `y`, `width`, `height` | `10, 20, 200, 40` | layout پیکسلی |
| `font_size` | `24` | اندازه متن |
| `color` | `#FFFFFF` | رنگ |
| `style` | JSON | تنظیم‌های ظاهری |
| `config` | JSON | تنظیم‌های اختصاصی widget |
| `z_index` | `1` | ترتیب render |

### 8.3 تغییر JSON UI

فرمت اصلی page و element را بی‌دلیل تغییر ندهید؛ firmware باید بر اساس `type` renderer داشته باشد. برای افزودن widget جدید:

1. `element_type` جدید، مثلاً `gauge` تعریف کنید.
2. schema مورد انتظار `config` را مستند کنید.
3. renderer آن را در ESP32 پیاده‌سازی کنید.
4. template آزمایشی بسازید.
5. دستگاه آزمایشی را با version جدید firmware آپدیت کنید.
6. سپس template را برای دستگاه‌های دیگر فعال کنید.

نمونه widget جدید:

```json
{
  "type": "gauge",
  "label": "Humidity",
  "source_key": "weather.humidity",
  "position": {"x": 20, "y": 120, "width": 120, "height": 120},
  "style": {"needle_color": "#00B7FF"},
  "config": {"min": 0, "max": 100, "unit": "%"}
}
```

### 8.4 تعریف منابع داده

هر `WordPressDataSource` باید داشته باشد:

```json
{
  "external_id": "weather-tehran",
  "key": "weather.tehran",
  "label": "Tehran Weather",
  "enabled": true,
  "config": {
    "provider": "openweathermap",
    "refresh_seconds": 900,
    "units": "metric"
  }
}
```

- `external_id`: شناسهٔ تغییرناپذیر sync.
- `key`: کلیدی که UI/worker برای data lookup مصرف می‌کند.
- `config`: تنظیم provider، interval، credential reference و mapping.
- secret provider را داخل JSON یا WordPress plaintext نگه ندارید؛ فقط reference یا environment variable نگه دارید.

> دریافت و cache واقعی دادهٔ providerها باید در task جداگانه اجرا شود؛ UI باید از key استاندارد استفاده کند، نه از جزئیات provider.

## 9. MQTT

وقتی config دستگاه provisioned تغییر کند، task غیرهمزمان پیام زیر را منتشر می‌کند:

```text
gadget/v1/devices/{external_id}/commands/config
```

Payload:

```json
{
  "type": "config.changed",
  "ui_version": 7
}
```

### رفتار لازم Firmware

1. به topic اختصاصی خودش subscribe کند.
2. بعد از دریافت `config.changed`، config API را با token خودش بخواند.
3. اگر `ui_version` جدیدتر بود، JSON را validate و persist کند.
4. `config_version` جدید را در heartbeat بعدی گزارش کند.
5. در صورت خطای parse/render، status را `error` و `error_message` را ارسال کند.

### امنیت MQTT در production

فایل فعلی Mosquitto برای local development anonymous است. برای production باید حتماً:

- `allow_anonymous false` شود.
- password file یا certificate device تعریف شود.
- TLS فعال شود.
- ACL نوشته شود تا device فقط این pattern را بخواند:

```text
gadget/v1/devices/{own-external-id}/#
```

- پورت MQTT public فقط پشت firewall/VPN یا با TLS expose شود.

## 10. OTA عملیاتی

### انتشار firmware

1. فایل firmware را build کنید.
2. SHA-256 محاسبه کنید:

```bash
shasum -a 256 firmware.bin
```

3. فایل را روی HTTPS storage/CDN قابل‌اعتماد قرار دهید.
4. در Django Admin، **Firmware Releases** را باز کنید.
5. `hardware_model`، `version`، URL، checksum، release notes، mandatory و active را وارد کنید.
6. ابتدا فقط روی یک device آزمایشی تست کنید.
7. deploymentها و heartbeatها را بررسی کنید.

### Rollback

اگر release مشکل داشت:

1. `is_active` release خراب را false کنید.
2. release پایدار قبلی را active کنید.
3. دستگاه‌ها را برای update check مجدد trigger کنید.
4. علت، error_message و firmware_version دستگاه‌های failed را در Admin تحلیل کنید.

> نسخه‌بندی semver (`MAJOR.MINOR.PATCH`) توصیه می‌شود، ولی مقایسهٔ semantic version فعلاً داخل سرور اعمال نمی‌شود. دستگاه باید فقط release معرفی‌شده را پس از checksum verification نصب کند.

## 13. تغییر API یا JSON بدون شکستن دستگاه‌ها

### قواعد compatibility

1. هیچ فیلد فعلی را بدون دورهٔ deprecation حذف یا rename نکنید.
2. فیلد جدید را optional اضافه کنید.
3. deviceهای قدیمی باید فیلد ناشناخته را ignore کنند.
4. تغییر breaking را با API version جدید مثل `/api/v2/` انجام دهید.
5. برای قرارداد UI، `effective_config.ui_version` را فقط در تغییر breaking افزایش دهید.
6. برای تغییر دادهٔ دستگاه، `WordPressDevice.ui_version` را افزایش دهید تا device config را refresh کند.

### روند استاندارد تغییر

```text
Schema proposal
  → نمونه JSON
  → Test backend
  → Test firmware simulator/device
  → انتشار backend
  → انتشار firmware سازگار
  → فعال‌سازی feature برای یک device
  → rollout تدریجی
```

### مثال: افزودن battery temperature

1. فیلد optional `battery_temperature_c` در payload heartbeat تعریف کنید.
2. validation و migration Django بنویسید.
3. firmware جدید مقدار را ارسال کند.
4. deviceهای قدیمی بدون این فیلد همچنان 200 بگیرند.
5. metric/Admin را بعد از دریافت داده اضافه کنید.

## 14. پاسخ‌های خطا

| HTTP | معنی | اقدام device/client |
|---:|---|---|
| `200` | موفق | ادامه |
| `202` | webhook پذیرفته شد | نیاز به retry فوری نیست |
| `400` | JSON یا field نامعتبر | firmware/client را اصلاح کنید |
| `401` | token یا signature نامعتبر | token/secret را بررسی یا rotate کنید |
| `403` | device inactive/suspended/unprovisioned | اپراتور باید وضعیت device را اصلاح کند |
| `404` | device یا firmware release وجود ندارد | external_id/hardware_model/version را بررسی کنید |
| `503` | service health down | با backoff retry کنید |

برای retry شبکه در ESP32 از exponential backoff استفاده کنید؛ مثلاً 5، 10، 20، 40 و حداکثر 300 ثانیه. برای خطاهای `400` retry کورکورانه انجام ندهید.

## 17. محدودیت‌ها و گام بعدی منطقی

این backend اکنون foundation کامل برای device auth، sync، UI، MQTT notification، OTA lifecycle و observability اولیه دارد. مواردی که هنگام رشد محصول باید جداگانه توسعه داده شوند:

1. **Device certificate / mTLS** به جای token تنها.
2. **MQTT ACL و TLS production** در broker و infrastructure.
3. **CDN/object storage و امضای cryptographic firmware** علاوه بر SHA-256.
4. **rollout percentage / cohort OTA** و rollback خودکار.
5. **دریافت واقعی دادهٔ providerها** و cache استاندارد برای Data Sourceها.
6. **Prometheus/Grafana، Sentry و alert delivery واقعی**.
7. **RBAC اختصاصی** به جای اتکای صرف به Django Admin.
8. **OpenAPI/Swagger** برای SDK و تیم firmware.

هر تغییر جدید باید با قرارداد JSON versioned، migration، test، documentation و rollout تدریجی انجام شود.
