# دریافت لحظه‌ای، بازر و تنظیم گرافیکی ارتباطات

این راهنما سیاست‌های قدیمی راهنمای ۱۸ درباره نگهداری داده، دریافت زنده و پیکربندی MQTT/HTTPS را جایگزین می‌کند. کد افزونه WordPress و Firmware در این تغییر دست نخورده‌اند.

## منابع اطلاعاتی بدون ویرایش کد یا JSON تنظیمات

در «منابع اطلاعات» نام، نوع API/وب/RSS/تلگرام، شرکت مالک، واحد، کلید نمایش، مسیر استخراج مقدار/عنوان، الگوی متن، عمر اعتبار و روش دریافت را تعیین کنید. اتصال احراز هویت از فهرست اتصال‌های همان مالک انتخاب می‌شود؛ کلید API در خود URL قرار نگیرد.

- **دوره‌ای:** سرور URL عمومی منبع را با فاصله تعیین‌شده می‌خواند. سهمیه و حداقل فاصله پلن همچنان رعایت می‌شود. دکمه آزمایش پس از ذخیره، مقدار استخراج‌شده را در فهرست منابع نشان می‌دهد.
- **لحظه‌ای:** برای API JSON، یک کلید امضای حداقل ۳۲ نویسه وارد کنید؛ سرویس ارائه‌دهنده یا واسط آن داده تازه را به `/api/v1/sources/{id}/push/` می‌فرستد. URL خروجی دوره‌ای در این حالت لازم نیست. این حالت push واقعی است، نه polling با نام لحظه‌ای. ارائه‌دهنده باید توان ارسال webhook داشته باشد؛ اتصال اختصاصی WebSocket هر صرافی یا سایتی در این نسخه وجود ندارد.

اعتبارنامه‌ها در «اتصال‌ها و توکن‌ها» رمزگذاری می‌شوند. مسیر API دستگاه‌ها و منابع وردپرس، مسیر پایه MQTT، نام هدر API و پیشوند آن، یا ارسال کلید در پارامتر query با نام قابل تنظیم اکنون فیلدهای جدا هستند و نیاز به نوشتن JSON ندارند. تغییر نوع اتصال، اعتبارنامه یا منبع باید با تنظیم واقعی سرویس مقابل هماهنگ باشد.

### قرارداد ورودی لحظه‌ای

```http
POST /api/v1/sources/42/push/
Content-Type: application/json
X-Source-Timestamp: <Unix timestamp of observation>
X-Source-Event: <unique event ID, max 100 characters>
X-Source-Signature: <hex HMAC SHA256>
```

امضا از الحاق بایت‌های `timestamp + "." + event_id + "." + raw_body` با کلید همان منبع ساخته می‌شود. بدنه خام JSON حداکثر ۶۴ KiB است و با مسیر استخراج فرم پردازش می‌شود. timestamp نباید بیش از پنج ثانیه در آینده یا بیش از کمینه TTL و ۳۰۰ ثانیه در گذشته باشد. امضای نامعتبر رد می‌شود؛ شناسه تکراری در پنجره اعتبار دوباره پردازش نمی‌شود؛ داده قدیمی‌تر جای جدیدتر را نمی‌گیرد. تغییر هم‌زمان تعریف منبع، دریافت در حال اجرا با تعریف قدیمی را باطل می‌کند. منابع خصوصی با انتخاب منابع مجاز هر دستگاه محدود می‌شوند.

بعد از دریافت، پردازش بازر و اعلان محتوای MQTT در صف قرار می‌گیرد؛ کار دوره‌ای نیز برای بازیابی پس از اختلال worker اجرا می‌شود. پنل در حالت لحظه‌ای SSE و در حالت دوره‌ای polling دارد. تغییر ساختار لیست‌ها یا اضافه شدن پیام، صفحه را تازه می‌کند؛ قیمت‌های موجود درجا تغییر می‌کنند. SSE اتصال احرازشده و محدود به دستگاه مجاز است و با لغو دسترسی متوقف می‌شود. پراکسی نباید پاسخ SSE را buffer کند. تأخیر شبکه/worker وجود دارد؛ تضمین hard real-time ارائه نمی‌شود.

## قوانین بازر

از جزئیات دستگاه یا دسترسی سریع صفحه شخصی وارد «هشدار و بازر» شوید. کاربران شخصی و مدیران شرکت برای دستگاه‌های مجاز خود، مستقل از پلن ساده/Pro، تا ۲۰ قانون می‌سازند:

| تنظیم | کاربرد |
| --- | --- |
| محدوده | همه اطلاعات، یک منبع انتخاب‌شده، یک کالای لیست قیمت یا پیام‌های شرکت |
| شرط | اطلاعات تازه، نوسان درصدی، نوسان مبلغی، عبور از سقف یا کف |
| جهت | افزایش، کاهش یا هر دو برای نوسان |
| آستانه | درصد یا واحد اصلی قیمت؛ مثل ۵ درصد یا ۱۰۰۰۰ تومان |
| مبنا | مقدار قبلی یا مرجع ابتدای بازه ۱، ۵، ۱۵ یا ۶۰ دقیقه |
| اولین دریافت | اختیاری؛ پیش‌فرض خاموش برای جلوگیری از بوق راه‌اندازی |
| الگوی بوق | مدت هر بوق ۵۰ تا ۳۰۰۰ میلی‌ثانیه، ۱ تا ۵ تکرار، فاصله بوق‌ها |
| کنترل مزاحمت | فاصله هشدارها، سقف تعداد در ساعت، روزهای فعال و ساعات سکوت |

مقایسه با Decimal و پشتیبانی از رقم فارسی انجام می‌شود. مقدار غیرعددی در قانون نوسان ارزیابی نمی‌شود. درصد نسبت به مقدار صفر محاسبه نمی‌شود. عبور از سقف/کف، crossing است؛ صرفاً ماندن آن سوی آستانه هشدار مکرر تولید نمی‌کند. ساعات سکوت از نیمه‌شب نیز عبور می‌کنند و طبق منطقه زمانی سامانه‌اند. وضعیت مبنا cache موقت است؛ پس از از دست رفتن cache، بازه از دریافت تازه آغاز می‌شود.

قانون خاموش/ویرایش‌شده، هشدارهای اجرا‌نشده قبلی خود را منقضی می‌کند. داده منقضی، دستگاه غیرفعال/تعلیق‌شده و کاربر غیرفعال بوق تازه تولید نمی‌کنند. سقف و cooldown برای مجموع اقلام هر قانون‌اند. قواعد متعدد مستقل‌اند؛ ممکن است دو قانون روی یک رویداد دو هشدار مستقل تولید کنند.

### قرارداد Firmware برای مرحله بعد

تنظیمات مؤثر `/display-config/` شامل `buzzer` و قوانین است. `mode=server_events` یعنی ارزیابی و تولید event سمت سرور انجام می‌شود؛ Firmware نباید همان قوانین را دوباره مستقل ارزیابی کند و دو بوق ایجاد کند.

رویداد `buzzer.alert` در `.../events/buzzer` بدون retain منتشر می‌شود و شامل `event_id`, `rule_id`, `expires_at`, `duration_ms`, `repeat`, `gap_ms` است. اطلاعات شرط نیز برای بررسی همراه آن می‌آید. نسخه معتبر و تأییدنشده رویداد در `/content/` زیر `buzzer_events` قابل دریافت است.

Firmware باید:

1. هشدار تکراری را با `event_id` حذف کند؛ QoS 1 تضمین عدم تکرار نیست.
2. هشدار منقضی را اجرا نکند؛ مهلت حداکثر ۳۰ ثانیه و حداکثر تا اعتبار اطلاعات است.
3. پس از اجرای موفق، `POST /api/v1/devices/{id}/buzzer/{event_id}/ack/` را با `X-Device-Token` بفرستد.
4. الگوی محدودشده بوق را اجرا کند. کنترل بلندی صدا/فرکانس فرض نشده، چون نوع سخت‌افزار بازر هنوز مبنای پیاده‌سازی Firmware نشده است.

سوابق در «سوابق هشدار» باقی می‌مانند. پذیرش MQTT با تأیید اجرای بوق فرق دارد. برای دستگاه آفلاین، بوق قدیمی در اتصال مجدد بازپخش نمی‌شود. بدون افزودن این قرارداد به Firmware آینده، سرور به‌تنهایی قادر به به‌صدا درآوردن بازر فیزیکی نیست.

## پیکربندی ارتباطات در پنل مدیر

در «ارتباطات سرور و گجت» موارد زیر قابل تنظیم‌اند:

- دامنه عمومی، فعال‌کردن HTTPS خودکار در استقرار مدیریت‌شده؛
- میزبان عمومی، پورت، TCP/WebSocket، TLS و مسیر WebSocket دستگاه‌ها؛
- فاصله heartbeat و مهلت تشخیص قطع ارتباط؛
- فاصله همگام‌سازی WordPress و اعتبار زمانی امضای webhook؛
- توکن‌ها، کلید امضا، آدرس WordPress، مسیر APIها و مشخصات ناشر MQTT در فرم اتصال‌ها.

سرور با تغییر این تنظیمات نسخه پیکربندی گجت‌ها را تازه می‌کند. رمز مشترک ناشر سرور هرگز در تنظیمات گجت قرار نمی‌گیرد. مسیر احرازشده `/api/v1/devices/{id}/connections/` نام کاربری اختصاصی `device-{pk}` و گذرواژه همان دستگاه را با `Cache-Control: no-store` می‌دهد. مدیر می‌تواند گذرواژه MQTT هر دستگاه را از جزئیات دستگاه تعویض کند؛ دستگاه باید از طریق توکن HTTPS خود اطلاعات تازه را بگیرد. تغییر دامنه‌ای که گجت دیگر به آن دسترسی ندارد، نیازمند دوره انتقال و نگهداری دامنه قدیمی است؛ جابه‌جایی خودکار دستگاه قطع‌شده ممکن نیست.

### استقرار مدیریت‌شده بدون ویرایش فایل‌های سرویس

`make guided` پروفایل دارای gateway را بالا می‌آورد. `make test-setup` فقط حالت خصوصی آزمایش را اجرا می‌کند. پس از شروع سرویس‌ها:

1. با تونل SSH یا روی خود میزبان به `http://localhost:8000/setup/` بروید و مدیر را بسازید.
2. در سرویس DNS، رکورد دامنه را به IP این سرور وصل کنید و ورودی ۸۰ و ۴۴۳ را باز کنید. DNS بیرون از این پروژه است و از صرف ذخیره نام دامنه تغییر نمی‌کند.
3. در فرم ارتباطات، دامنه `https://...` و گزینه HTTPS خودکار را ثبت کنید.
4. Caddy فقط برای همان دامنه تأییدشده توسط برنامه گواهی می‌گیرد. پورت ۸۰۰۰ همچنان loopback است و مسیر داخلی تأیید دامنه از gateway عمومی مسدود است.
5. MQTT دستگاه‌ها در این پروفایل با **WSS روی پورت ۴۴۳ و مسیر `/mqtt`** در دسترس است. اتصال ناشر سرور به broker داخل شبکه خصوصی Docker است. TCP/TLS مستقیم برای broker خارجی نیز در فرم قابل انتخاب است، ولی حساب و گواهی آن broker خارجی باید توسط مدیر همان سرویس ایجاد شود.
6. سرویس `broker_config` با `mosquitto_passwd -U` فایل‌های hash و ACL را تولید می‌کند؛ گذرواژه در argv یا لاگ قرار نمی‌گیرد. هر دستگاه فقط پیام‌های خودش را می‌خواند و فقط telemetry خودش را می‌نویسد. حساب ناشر دسترسی به مسیر پایه سامانه دارد.
7. اعمال تغییر حساب‌ها، لغو دسترسی و چرخش رمز، broker مدیریت‌شده را بازراه‌اندازی می‌کند تا نشست‌های قبلی نیز قطع شوند. دستگاه‌ها باید reconnect داشته باشند. فایل‌های broker نیازی به ویرایش دستی ندارند. تغییرات معمولاً در چرخه پنج‌ثانیه‌ای اعمال می‌شوند.

برای استقرار قبلی دارای Nginx یا اشغال پورت ۸۰/۴۴۳، gateway مدیریت‌شده را هم‌زمان روی همان پورت اجرا نکنید؛ انتقال سرویس باید برنامه‌ریزی شود. صدور واقعی گواهی، اجرای ابزار hash، پذیرش MQTT و reconnect دستگاه باید روی میزبان مقصد آزمایش شود. این محیط اجرای Docker نداشته است.

مبنای پیکربندی: [Caddy on-demand TLS](https://caddyserver.com/docs/caddyfile/options#on-demand-tls)، [Mosquitto authentication](https://mosquitto.org/documentation/authentication-methods/) و [mosquitto_passwd](https://mosquitto.org/man/mosquitto_passwd-1.html).

## نگهداری داده و لاگ‌ها

- **پاک‌سازی خودکار AuditEvent، WordPressSyncEvent، SyncNotification، سابقه ارسال و سابقه بازر حذف شد.** فیلد قدیمی مهلت لاگ دیگر در فرم تنظیمات ارائه و در پاک‌سازی استفاده نمی‌شود.
- پیام شرکت و قیمت دستی به‌طور پیش‌فرض حیاتی/ماندگارند. فقط با انتخاب صریح «داده موقت؛ پس از انقضا قابل پاک‌سازی است» مقدار منقضی آن رکورد پاک می‌شود؛ شناسه و metadata باقی می‌مانند.
- قیمت منقضیِ محفوظ در SQL، در API یا صفحه مشتری به عنوان قیمت جاری نمایش داده نمی‌شود.
- نشست‌های ورود منقضی نیز داده موقت محسوب می‌شوند؛ سابقه ورود و رویدادهای ثبت‌شده پاک نمی‌شوند.
- مدیر می‌تواند پاک‌سازی داده‌های موقت را کاملاً خاموش کند. گزینه پاک‌سازی به لاگ‌ها تعمیم داده نمی‌شود.
- آخرین نمونه لحظه‌ای منابع و state مقایسه بازر، cache موقت دارای TTL هستند؛ پاسخ خام منابع و توکن‌ها در لاگ ذخیره نمی‌شوند.
- حذف بدنه سوابق موجود از migration قبلی ۰۰۱۱ برداشته شد. اگر نسخه قبلی واقعاً اجرا شده و داده‌ای پاک شده باشد، این تغییر آن را از هیچ بازسازی نمی‌کند؛ بازیابی نیازمند backup است.
- ارتقای ۰۰۱۲ داده‌های حیاتی جدید را به‌طور پیش‌فرض قابل حذف علامت نمی‌زند.
