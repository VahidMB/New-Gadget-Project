# پنل قیمت و مدیریت گجت — راهنمای نسخه جدید

> بخش‌های نگهداری داده، دریافت زنده و ارتباطات این سند با [راهنمای ۱۹](19-live-buzzer-connections.md) جایگزین شده‌اند. لاگ‌ها اکنون پاک نمی‌شوند و داده‌های حیاتی پیش‌فرض محفوظ‌اند.

این نسخه روی اصلاحات شاخه `fix/device-platform-reliability` ساخته شده است. فایل‌های Firmware مربوط به ESP32 در این مخزن وجود ندارند؛ این مخزن سرور، پنل‌ها و قرارداد ارتباطی را ارائه می‌کند.

## راه‌اندازی بدون ویرایش فایل‌های تنظیمات برنامه

روی میزبان دارای Docker Compose و Python 3:

```bash
make guided
# محیط جداگانه برای ارزیابی اولیه:
make test-setup
```

اسکریپت `scripts/guided_setup.py` رازهای زیرساخت را خودکار تولید و فقط روی همان میزبان نگه می‌دارد. سرویس وب روی `127.0.0.1:8000` باز می‌شود. صفحه `/setup/` کد یک‌بار راه‌اندازی درج‌شده در لاگ API را می‌خواهد و حساب مدیر را می‌سازد. برای سرور راه دور از تونل SSH استفاده کنید. پس از ثبت مدیر، مسیر راه‌اندازی دوباره قابل تصاحب نیست.

این دستور برای **راه‌اندازی خصوصی و تنظیم اولیه** است. عمومی کردن دامنه نیازمند DNS، HTTPS و MQTT دارای TLS و ACL است؛ ذخیره دامنه در پنل به‌تنهایی گواهی یا DNS ایجاد نمی‌کند. پروفایل موجود `deploy/linux/docker-compose.production.yml` برای استقرار دارای TLS حفظ شده است. TLS را روی پراکسی ورودی خاتمه دهید و پورت داخلی وب را عمومی نکنید. راه‌اندازی واقعی کانتینرها باید روی میزبان مقصد بررسی شود.

توکن‌ها و اتصال‌های کاربردی در «اتصال‌ها و توکن‌ها» قابل تغییرند. اعتبارنامه‌های قدیمی محیط، در اولین اجرای `initialize_platform` به صورت رمزگذاری‌شده وارد جدول اتصال‌ها می‌شوند؛ اجراهای بعدی مقادیر مدیر را بازنویسی نمی‌کنند.

| کلید اتصال | کاربرد | گزینه‌های تکمیلی |
| --- | --- | --- |
| `wordpress` | آدرس، Bearer token و کلید امضای وب‌هوک | `devices_endpoint`, `sources_endpoint` |
| `wordpress-sync` | توکن فراخوان همگام‌سازی | ندارد |
| `mqtt` | میزبان، پورت، TLS، نام کاربری و گذرواژه ناشر سرور | `topic_root` |
| `notifications` | آدرس اعلان رویدادهای همگام‌سازی | ندارد |
| `metrics` | توکن دسترسی به خروجی Prometheus | ندارد |
| `monitor` | توکن دریافت نمونه مصرف منابع | ندارد |
| کلید دلخواه با نوع `provider` | اعتبارنامه یک منبع API | `auth_header`: `Authorization` یا `X-API-Key`، `auth_scheme` اختیاری |
| کلید دلخواه با نوع `telegram` | توکن و کلید وب‌هوک ربات یک شرکت یا کتابخانه عمومی | ندارد |

برای منبع دارای اعتبارنامه، آدرس `endpoint` اتصال provider باید میزبان و طرح URL مجاز را تعیین کند. تغییر آدرس منبع به دامنه دیگر باعث انتقال توکن به آن دامنه نمی‌شود. مشتری توکن مدیر را نمی‌بیند. خالی گذاشتن فیلد رمز در فرم، رمز قبلی را حفظ می‌کند؛ حذف، انتخاب جداگانه دارد.

کلید اصلی رمزگذاری و راز Django خودکار خارج از دیتابیس و در فضای `runtime` با دسترسی محدود ساخته می‌شوند. این فضای مشترک باید همراه دیتابیس پشتیبان‌گیری شود؛ از دست رفتن کلید اصلی، بازیابی توکن‌های رمزگذاری‌شده را ناممکن می‌کند. کلید ریشه، گذرواژه دیتابیس، DNS و گواهی‌های میزبان عمداً از تنظیمات عادی کاربردی جدا هستند. تغییر اعتبارنامه اتصال MQTT در پنل، حساب کاربری خودِ Mosquitto را ایجاد نمی‌کند؛ حساب ناشر و ACL دستگاه‌ها باید روی broker برقرار باشد.

## ترتیب تنظیم اولیه در پنل

1. نام سامانه، منطقه زمانی، دامنه و مهلت تشخیص قطع ارتباط را تعیین کنید.
2. پلن ساده و VIP/Pro، سهمیه API/وب/RSS، سهمیه تلگرام و حداقل فاصله دریافت را تنظیم کنید.
3. حساب شخصی یا شرکت بسازید؛ برای نمایندگی، شرکت مادر را مشخص کنید.
4. کاربر و عضویت او را بسازید. دستگاه را به شرکت مالک و در صورت نیاز به کاربر استفاده‌کننده اختصاص دهید.
5. منابع عمومی را تعریف و آزمایش کنید؛ سپس قالب‌ها، صفحات و عناصر هر پلن را تنظیم کنید.
6. دستگاه را ثبت و توکن آن را صادر کنید. توکن فقط یک بار نمایش داده می‌شود و فقط هش آن در دیتابیس ذخیره می‌شود.
7. در شرکت Pro، گروه و نام نماینده دستگاه‌ها، لیست قیمت و پیام زمان‌بندی‌شده را تعیین کنید.

## حساب‌ها و مرز دسترسی

- مالک دستگاه، حساب شخصی یا شرکت است؛ کاربر اختصاص‌یافته و پلن دستگاه، فیلدهای مستقل هستند.
- مدیر یا اپراتور شرکت، دستگاه‌های شرکت و نمایندگی‌های فعال آن را می‌بیند. کاربر عضو عادی فقط دستگاه‌های اختصاص‌یافته خود را می‌بیند. عضویت غیرفعال دسترسی را قطع می‌کند.
- مدیر سرور می‌تواند کاربران، عضویت‌ها، پلن‌ها، دستگاه‌ها، منابع و قالب‌ها را تغییر دهد. کنترل توکن دستگاه و اتصال‌های سامانه برای مالک پلتفرم است.
- شرکت می‌تواند هم‌زمان دستگاه ساده و Pro داشته باشد. مدیریت گروهی مشتری و ارسال پیام به دستگاه Pro نیاز دارد؛ داشتن یک دستگاه Pro، مجوز دور زدن پلن سایر دستگاه‌ها نیست.
- تعلیق مدیر سرور با `is_active`/`provisioning_state` جدا از `customer_enabled` است. مشتری نمی‌تواند تعلیق مدیر را رفع کند.
- وضعیت ارتباط «آنلاین»، «قطع ارتباط»، «غیرفعال» یا «تعلیق» است. قطع ارتباط به معنی اثبات خاموشی برق نیست.
- باتری از مدل و پنل حذف شده است. heartbeat قدیمی که فیلد باتری بفرستد، آن فیلد را نادیده می‌گیرد.

## دریافت قیمت و اطلاعات

منابع می‌توانند قیمت، خبر، هواشناسی یا متن باشند. برای API، مسیر نقطه‌ای JSON مانند `data.0.price`؛ برای HTML، انتخابگر CSS مانند `.price`؛ برای RSS، نام فیلد مانند `description` تعریف می‌شود. استخراج بخش متن با الگوی دارای گروه اول مانند `قیمت: ([0-9]+)` انجام می‌شود. اجرای الگو محدودیت زمانی دارد. HTML وابسته به اجرای JavaScript استخراج نمی‌شود؛ از API سایت یا خروجی HTML سرور استفاده کنید.

دریافت منابع عمومی فقط از HTTP(S)، پورت ۸۰/۴۴۳ و IP عمومی انجام می‌شود. DNS قبل از اتصال بررسی و اتصال به IP اعتبارسنجی‌شده متصل می‌شود. redirect دنبال نمی‌شود، حجم پاسخ حداکثر یک مگابایت است و زمان اتصال محدود است. این محدودیت‌ها برای جلوگیری از دسترسی منبع کاربر به شبکه داخلی سرور است.

کاربر ساده از منابع عمومی مدیر انتخاب می‌کند. کاربر Pro با سهمیه مدیر منبع اختصاصی می‌سازد؛ تعداد منابع API/وب/RSS و تلگرام جداگانه محاسبه می‌شود. منابع خصوصی به حساب دیگر منتقل نمی‌شوند. بعد از تنزل پلن یا کاهش سهمیه، محتوای خروجی و تنظیمات دستگاه همان محدودیت تازه را رعایت می‌کنند.

فاصله **دریافت داده** مستقل از فاصله **تعویض محتوای نمایشگر** است. مثلاً نمایشگر هر ۳۰۰ ثانیه صفحه عوض می‌کند، در حالی که منبع هر ۳۰ ثانیه تازه می‌شود. گزینه «به‌روزرسانی زنده» اعلان تغییر محتوا و تازه‌سازی خودکار پنل را فعال می‌کند. پنل با فاصله مجاز پلن polling می‌کند؛ دستگاه رویداد MQTT دریافت می‌کند. این سامانه تضمین hard real-time یا اتصال مستقیم به جریان WebSocket صرافی ارائه نمی‌کند؛ تازگی به تأخیر منبع و فاصله دریافت آن بستگی دارد.

قیمت به همراه واحد، منبع، `observed_at` و `expires_at` برگردانده می‌شود. مقدار منقضی هرگز به عنوان قیمت معتبر نمایش داده نمی‌شود، حتی اگر دریافت بعدی شکست بخورد. زمان و ترتیب منابع در پنل محتوا قابل تغییر است.

## نگهداری و انقضا

- پاسخ خام API/سایت/تلگرام در دیتابیس SQL ذخیره نمی‌شود. آخرین مقدار استخراج‌شده فقط در cache دارای TTL است؛ اجرای Redis بدون RDB/AOF برای این داده‌ها ضروری است و در پروفایل‌های جدید اعمال شده است.
- SQL فقط تعریف منبع و زمان/نتیجه دریافت را نگه می‌دارد. رخداد WordPress فقط metadata و هش دارد، نه بدنه خام دریافتی.
- قیمت دستی شرکت و متن پیام تا زمان اعتبار در SQL هستند. از لحظه انقضا، تمام مسیرهای نمایش و API مقدار را مخفی می‌کنند. کار دوره‌ای هر ۳۰ ثانیه مقدار قیمت را `NULL` و متن پیام را خالی می‌کند؛ اگر worker خاموش باشد، پاک‌سازی فیزیکی تا بازگشت آن به تأخیر می‌افتد ولی مقدار منقضی سرو نمی‌شود.
- شناسه کالا، واحد، گیرندگان و سوابق عملیات بدون متن قیمت/پیام باقی می‌ماند. این سازوکار تضمین پاک‌شدن همان لحظه از backup یا صفحات داخلی PostgreSQL نیست.
- در ارتقا، پیام قدیمی بدون انقضا مهلت ۲۴ ساعته می‌گیرد. سوابق عملیات طبق مهلت قابل تنظیم مدیر پاک می‌شوند.

## قرارداد گجت

تمام مسیرهای اختصاصی دستگاه هدر `X-Device-Token` می‌خواهند. دستگاه غیرفعال، تعلیق‌شده، متعلق به حساب غیرفعال یا با کاربر غیرفعال پذیرفته نمی‌شود.

| مسیر | روش | نتیجه |
| --- | --- | --- |
| `/api/v1/devices/{id}/display-config/` | GET | قالب مؤثر، نسخه تنظیمات، منابع انتخابی، سهمیه‌ها، رنگ و زمان‌بندی |
| `/api/v1/devices/{id}/content/` | GET | فقط داده معتبر، لیست قیمت‌های هدف و پیام‌های منقضی‌نشده؛ `Cache-Control: no-store` |
| `/api/v1/devices/{id}/heartbeat/` | POST | وضعیت، نسخه firmware، قدرت سیگنال و نسخه تنظیمات؛ بدون باتری |
| `/api/v1/devices/{id}/firmware/update-check/` | GET | نسخه سازگار جدیدتر؛ بدون تنزل خودکار |
| `/api/v1/devices/{id}/firmware/{release_id}/download/` | GET | دانلود احرازشده فایل بارگذاری‌شده و منتشرشده برای مدل دستگاه |
| `/api/v1/devices/{id}/firmware/update-report/` | POST | گزارش وضعیت نصب طبق قرارداد OTA قبلی |

MQTT پیش‌فرض: `gadget/v1/devices/{external_id}/commands/config` برای تغییر نسخه تنظیمات، `.../events/content` برای اعلان تغییر محتوای معتبر، `.../commands/message` برای پیام شرکت. اعلان محتوا شامل `type=content.changed`، هش `revision` و `fetch_path` است؛ دستگاه باید با توکن خودش داده تازه بگیرد. رویدادهای محتوا و پیام retained نیستند. مقدارهای cache، قیمت‌های SQL و محتوای MQTT همگی باید در firmware در پایان `expires_at` حذف شوند؛ آخرین داده نباید بعد از قطع شبکه روی نمایشگر معتبر جلوه کند.

MQTT QoS 1 ممکن است تکرار داشته باشد. دستگاه باید پیام را با `campaign_id` و تنظیمات را با نسخه deduplicate کند. ثبت `delivered_at` در سرور به معنی قبول انتشار توسط broker است، نه تأیید نمایش روی دستگاه. ارسال ناقص برای گیرنده ناموفق تکرار می‌شود؛ ارسال موفق دوباره عمداً اجرا نمی‌شود، ولی شکست اتصال پس از پذیرش broker همچنان ممکن است تکرار ایجاد کند. اتصال مجدد باید شامل دریافت `/content/` باشد.

## قرارداد تلگرام؛ آماده برای مرحله ساخت ربات

خود ربات تعاملی در این مرحله ساخته نشده است. سرور، دریافت امن و استخراج محتوا را آماده کرده است:

1. مدیر یک Integration با نوع `telegram`، کلید یکتا، شرکت مالک، توکن ربات و کلید webhook تعریف می‌کند.
2. مسیر callback برابر `/api/v1/integrations/telegram/{key}/webhook/` است.
3. ثبت webhook روی Telegram در مرحله ربات با `secret_token` انجام می‌شود. درخواست ورودی باید هدر `X-Telegram-Bot-Api-Secret-Token` مطابق کلید رمزگذاری‌شده داشته باشد.
4. قالب استاندارد `update_id` و یکی از `channel_post`, `edited_channel_post`, `message`, `edited_message` پذیرفته می‌شود؛ `chat.id`, `date`/`edit_date`, `text`/`caption` استخراج می‌شوند.
5. منبع تلگرام باید همان شرکت، شناسه chat و `credential_reference` برابر کلید ربات داشته باشد. مشتری فقط در صورت وجود دقیقاً یک اتصال فعال شرکت می‌تواند منبع تلگرام اضافه کند؛ انتخاب چند ربات توسط مدیر تعیین می‌شود.
6. ربات باید به کانال/گروه مجاز دسترسی داشته باشد. تاریخ اولیه پیام، عمر اعتبار آن را تعیین می‌کند؛ ارسال دوباره پیام قدیمی باعث زنده شدن آن نمی‌شود. update تکراری تا ۲۴ ساعت رد و داده قدیمی‌تر جای داده جدیدتر را نمی‌گیرد.
7. API دریافت فرمان از مشتری در تلگرام، ثبت حساب و مکالمه ربات متعلق به مرحله بعد است. توکن گجت نباید در پیام تلگرام فرستاده شود.

## همگام‌سازی مالکیت از WordPress

قرارداد موجود حفظ شده و فیلدهای اختیاری `company_slug`, `assigned_username`, `recipient_name`, `recipient_contact`, `group_name` به payload دستگاه اضافه شده‌اند. شرکت و کاربر باید از قبل در پنل موجود باشند و کاربر عضو فعال همان شرکت باشد. `assigned_username` خالی تخصیص را پاک می‌کند. تغییر شرکت بدون تعیین کاربر، تخصیص قدیمی را پاک می‌کند. نبود این فیلدها مالکیت موجود را تغییر نمی‌دهد. افزونه واقعی WordPress باید این فیلدها را ارسال کند؛ کد آن افزونه در این مخزن نیست.

## سلامت و مصرف منابع

داشبورد API، دیتابیس، Redis، اتصال TCP broker، پاسخ worker و اتصال WordPress را نشان می‌دهد. وضعیت Telegram از آخرین webhook معتبر به دست می‌آید؛ این مورد صرفاً فعالیت اخیر است، نه probe مستقل Telegram. مقدار قدیمی‌تر از ۱۸۰ ثانیه «نامشخص» می‌شود. اگر collector داده ندارد، مصرف صفر ساخته نمی‌شود.

`collect_resources --loop` CPU و مجموع RSS فرایندهای تشخیص‌داده‌شده هر سرویس را هر ۳۰ ثانیه ثبت می‌کند. در پروفایل guided، collector فقط‌خواندنی با namespace فرایندهای میزبان اجرا می‌شود. این اندازه‌گیری process-based است؛ حافظه اشتراکی ممکن است چندبار شمرده شود و فرایند هم‌نام متعلق به برنامه دیگر نیز ممکن است در گروه قرار بگیرد. برای انتساب دقیق container/cgroup، از collector میزبان با API زیر استفاده کنید:

```http
POST /api/v1/monitoring/resources/
Authorization: Bearer <monitor integration secret>
Content-Type: application/json
```

```json
{"services":[{"service":"api","status":"up","cpu_percent":12.5,"memory_bytes":100000000,"disk_bytes":200000000,"network_rx_bytes":10000,"network_tx_bytes":12000}]}
```

حداکثر ۵۰ سرویس در درخواست، مقادیر غیرمنفی و محدود. فیلد اندازه‌گیری‌نشده را `null` بفرستید. CPU می‌تواند به‌دلیل چند هسته بیشتر از ۱۰۰٪ باشد. دیسک و شبکه از collector بیرونی دریافت می‌شوند؛ collector فرایندی داخلی این دو را حدس نمی‌زند. نمونه‌های سرویس سفارشی نیز در پنل نمایش داده می‌شوند. این نسخه تاریخچه نموداری مصرف را ذخیره نمی‌کند.
